## 2026-08-14 — `@all` 被拦时也要说话

`post_cascade_capped` 增加 `dropped_everyone`。

`_extract_team_mentions` 的返回是**二选一**：要么 `["@everyone"]`，要么一串 agent_id，
不会混。所以 agent 说 `@all` 又撞上 hop cap 时，`dropped` 恰好是空列表，函数直接 return，
房间一个字都没说——而这正是这个文件开头描述的那个场景（"用户要求把人拉进来，平台拒绝了，
没人说一声"），只不过换成了六人房间**最常用**的那种叫法，也是最容易把 hop 深度推到上限的
那一种。

**不能**把 `@everyone` 原样塞进 `dropped`：文案会渲染成 "@everyone was not pulled in"，
那是一句关于不存在的人的话。所以它是自己的一个 bool，文案说的是"团队里其余的人没有被拉
进来"。

顺带修掉复数：`", ".join(dropped)` 加上 "was" 在两个人以上时是 "Ana, Bruno was not
pulled in"。这行字存在的意义就是给人读、然后据此行动的。

# team_notices — 平台对团队房间做过、却从没说出口的事

## 为什么存在

三件都是**正确的行为**，但从房间里看起来像别的事：

**级联封顶。** agent 跳数堆到上限后，平台停止传播 @mentions，防止两个 agent 无限互唤。
这个保护是对的——但它只记在服务端日志里。**从房间里看，就像 agent 请队友帮忙、队友装作没看见。**
用户明确要求把某人拉进来，平台拒绝了，而没有任何人说过这件事。

**成员与 lead 变更。** 谁在房间里决定 `@all` 能触达谁、谁能回答；lead 决定没人被 @ 时谁回答、
巡查唤醒谁。两者都在静默变化，**而且会让变更之上的整段 transcript 读起来像是当前这批人写的**。

## 每条通知都照 `system_stop` 的四点先例

理由每次都一样，所以写在一处：

- `msg_type` 标记它 → 前端渲染成居中行，而不是带身份色的气泡；
- `content` 存英文兜底 → 数据库不知道读者的语言，但只读文本的消费者仍会读它；
- **不带 mentions**。对级联通知这一条是**承载语义**的，不是整洁：它存在的前提就是链条必须停下，
  唤醒任何人都会重启它被发出来打断的那个循环。对成员变更，加一个成员不该立刻给他派一轮活。
- 注册进 [[system_messages]] → 被排除在总结触发、transcript 的发言者渲染、**以及 agent 跳数**之外。
  **一条计入跳数的封顶通知，会让上限每次触发后都更紧。**

## 级联通知点名「谁没被拉进来」

「达到了某个上限」不可行动；「Bruno 没有被拉进来」告诉用户该自己去 @ 谁——
**这正是告诉他的全部意义**。`@everyone` 被排除在名字之外：它不是队友，
把它塞进「X 没被拉进来」会造出一个关于不存在的人的句子。

什么都没被丢弃时不发通知——宣告一个没触发的上限，会训练读者忽略这一行。

## 与 turn 失败的区别（值得写下来，避免误认为这里也修了它）

turn 失败**本来就落墙了**：trigger 返回一段 `⚠️ I couldn't process...` 当作回复发出去。
缺的不是可见性，是**正确的归属**——它以 agent 自己的名字和颜色发出，就像 agent 说了这句话。
