# test_im_dm_fallback_loop_guard.py — 兜底不能变成乒乓引擎

钉 [[step_3_agent_loop.py]] 新增的两道 DM 兜底前置门
（`agent_peer_no_fallback` / `fallback_rate_limited`）。

**第一条测试是基线**：人类 DM 照旧拿到兜底。这批改动最大的风险不是漏拦，
是把 0802 的修复顺手推翻。

**理由优先级也被钉住**：对端是 agent 但这轮已经有机发过回复 → 报
`already_replied_via_tool`（实际发生的事）而不是
`agent_peer_no_fallback`（我们本来也会拒绝的事）。报告要说最具体的那个。

新增一组**端到端断言**：prompt 半边说「可以沉默」、运行时半边确实不再覆盖
它（对 agent 对端），以及人类 DM 那半仍然保住 0802 的修复。钉端到端是因为
**两半各自都是绿的而链条是断的**——prompt 说一套、运行时做一套，没有任何
测试会失败。同组还钉住 #359 留下的旧警告不得残留。

计数器按 `agent_id:channel:room_id` 分桶：一个吵闹的房间不能把别的房间也堵上；
拿不到身份时返回空 key 并**不计数**，否则所有无法识别的对话会挤进同一个
共享桶里互相饿死。

## 审计侧钉什么，为什么

`fallback_rate_limited` 的窗口是**纯进程内、重启即清零**的，所以「这个对话被
压掉了多少条回复」事后只能从 DB 行恢复——而对面那个人看到的就是 0802 症状
（助手不理我了），owner 一定会问为什么。

- **payload 字段名与 reason**：运维几周后 SELECT 的就是它们。
- **`(reason, 会话键)` 冷却**：写入速率由外部对端决定，不冷却的话一条被喂着
  的对话每天约 1.9 万行，而 `service_audit` **没有保留策略**。键含 reason ——
  两道门是两件不同的事，共用槽会让后发生的被前一件吃掉。
- **写失败不占冷却槽**：`ServiceAuditor.event()` **永不抛**（`_emit` 内部就
  吞了），所以「没抛异常」不等于「写进去了」。第一版据此 arm 冷却，等于 DB
  抖一下这个对话整窗失声；而那条测试用一个**会抛的 fake** 钉绿了一个只有
  fake 才具备的性质。现在 `event()` 返回成败，fake 也照同一个契约返回。
- **只审计新增这两个 reason**：另外三个都能从这一轮的数据重算，审计它们是
  噪声。这条是**行为断言**（走 `_maybe_audit_fallback_skip`），不是读源码——
  「顺手把五个都审计上」是个容易且错误的清理。
- **`suppressed_since_last_row` 的账要能收干净**：钉三条路——对话继续下去
  （下一行带出来）、对话在冷却窗口内结束（回收时补一行 `final_tally`）、
  同一对话两轮交错（两行合计不超过两轮）。只钉第一条的话，最常见的那种
  短对话会静默丢账，而这个字段存在的意义正是让阈值下次按数据重定。

## 两个测试自身的坑（都真实发生过）

1. **fake 与真实协作者的契约不一致**：见上面「写失败」那条。fake 能做真实
   协作者做不到的事时，绿灯毫无意义。
2. **setup 遮住了被测行为**：验证「写成功后清零」时曾把冷却设成 0 图省事，
   结果剪枝把计数器一并删了，**清零与否都看不出**——变异验证当场发现它不会
   红。改用假时钟推进，冷却保持真实值。

测试里**刻意不让 `ServiceAuditor` 真写 DB**：真实例会 `await get_db_client()`
然后被 never-raise 吞掉，断言「没抛异常」永远绿。

## 已知残留

`step_3_agent_loop` 里**调用** `_maybe_audit_fallback_skip` 的那一行仍然只有
源码断言——它在 generator 的 skip 分支深处，驱动到那里要 stub 掉
ContextRuntime 与整个 agent loop。判定与 payload 组装已经抽成具名函数并被行为
测试覆盖，剩下的是那一跳本身。本文件的注释里记了两次恰好死在这类跳上的事故，
所以这个残留是**写明的**，不是默认的。

## 假时钟为什么不 patch `time.monotonic`

`step_3` 用的是 `import time`，所以给 `time.monotonic` 打桩会**同时**给
asyncio 事件循环打桩——进程里每个 timeout 和 sleep 都会读到一个冻住的时钟。
`_install_fake_clock` 改的是 `step_3` 自己命名空间里的 `time` 这个名字，
假货被关在被测代码里。

## 两张审计 map 的上界各有一条测试

上界测试和别的不一样：它钉的不是某次调用的结果，而是**进程跑几天之后**的
形状。两张 map 都以对端提供的 `room_id` 为键，而 gate 1 在 A2A 对话的每一
轮都会触发（不需要任何错误条件），所以"每个房间留一条"就是泄漏。

写失败那条路单独钉一次，因为它是增长最快的条件：写不进去 → 冷却不 arm →
每一轮都自增。第一版把扫描挂在"落库成功之后"，等于最需要回收的时候回收不
运行。

保留期是冷却窗口的 2 倍，这个倍数被一条测试钉着（改回 1x 会红）——计数器欠
的是下一行的账，下一行最早在冷却到期那一刻落，同窗口回收会在到期瞬间销账。

三条与收尾路径相关的钉子，都是「链条断开而全测试绿」的方向：

1. **被冷却的回合也要收尾**。三条原有测试最后一次调用的会话键都是全新的，
   必然未被冷却，所以把 `await` 挪到早退 `return` 之后**全部 33 条仍然绿**。
   新测试让一个正在冷却中的会话去承担收尾（X 冷却未过期、Y 已过保留期），
   挪动即红。
2. **超限条目下一次 sweep 立刻排空**，且断言时**不推进时钟**——推进时钟的
   排空循环会让「pop 后塞回、刷新 touched」照样通过（续期后的条目再等一个
   保留期又会到期），第一版就是这样，变异全绿。
3. **丢掉的收尾行必须留下数值**。用仓库既有的 loguru sink 夹具
   （`log_lines`）而不是 `caplog`——loguru 不走 stdlib logging。

回收本身**不是**账的终点：还欠着的条目会被交出来补一行 `final_tally` 收尾。
「回收 40 个 key」那条测试因此必须把**行数**也断言上（40 行收尾），否则
fake auditor 不数行数，收尾路径整个是空实现也能静默通过。另外那条测试特意
让每个房间压制**两次**——只压一次的话第一轮当场落行、账已清零，测试会在
收尾路径根本不存在时照样绿。

## 认不出会话身份的那类行

不上冷却，所以每条都写，且 `suppressed_since_last_row` 写 **1** 不是 0——
它就代表它自己那一轮，与可识别行同一个口径。写 0 会让这个字段在这类行上恒
为常数，也就是 `window_count` 被批的那件事换个名字重来。

测试同时断言**两张 map 都没留下东西**：给空身份上冷却会把所有这类轮次塞进
同一个槽，第一条把其余全部静音——那正是限流键上一轮修掉的共享桶形状，不能
在审计面上重新长出来。
