# latency_report.py — 验收①的那张成绩单（读日志，不读表）

## 为什么存在

PRD《Team 群聊响应速度》验收①要「改前/改后实测对比数据」。`[bus-timing]` /
`[turn-timing]` 从 2026-08-05 起就在打这些数，本脚本把它们变成一句能拍板的话。
入口：`make latency-report`（可带 `HOURS=` / `CHANNEL=`）。

## 为什么不建表（这一条最值得记住）

本次工作**先建了** `bus_hop_timing` / `turn_timing` 两张表，随后**撤回**了。撤回的
理由要写清楚，免得有人再走一遍：

**引表时用的论据是错的。** 当时引「教训 #5：日志会轮转掉，用 DB」。但那条教训针对的是
`docker logs`。**本项目早就把日志留存解决了**——loguru 按服务写文件，
`rotation="00:00"` + `retention="30 days"`（见 `utils/logging/_setup.py`）。

**日志确实够用，实测过。** 一行 `grep + awk` 从日志文件算出的 team 房
`p50=7.78s p90=11.33s`，与表版本报表的输出**逐位一致**。而本次「并行不值得做」这个
判断，本身就是直接扒日志得出的，全程没碰表。

**表买到的东西是**：跨信号 JOIN（hop → turn → 路由决策，靠 `event_id`）和自解释的
SQL。**代价是**：两张表 + 两个 repository + 两处热路径写入 + 一次迁移。为一次延迟排查
付这个，不划算。（顺带澄清一个我自己也搞错的点：反对理由**不是**性能——实测一次
INSERT p50 仅 0.09ms，对 24 秒一跳可忽略。理由是代码面积。）

**什么时候该建**：如果延迟成为长期盯的指标，该建的是 `turn_timing`——秒数在 setup 段
——而不是这一整层。hop 那张表的窗口很短，日志足够。

**保留的例外**：`narrative_routing_audit` 的四个 `*_ms` 列**留着**。那张表本来每次决策
就写一行，加四个可空列的边际成本是零，而它给出的「成本 ↔ 决策」关联（短路的决策 vs
叫了 judge 的决策）是日志给不了的。

## 设计决策

**直接打印验收①的判定**（team 房 `queue_wait` 的 p50/p90 与 30s 阈值比，输出
PASS/FAIL）。口径注意：`queue_wait` **不含 turn**，因为验收①写的是「消息 → 触发 →
开始处理」。

**分位数用 nearest-rank，不插值。** 样本量是几十到几百，插值出来的 p90 是谁都没经历过的
延迟；nearest-rank 保证每个数都真实发生过。测试里断言「结果必须是样本之一」。

**哨兵行整片剔除并单独计数。** `-1.00` 解析成 `-1000` 而不是四舍五入成像样的数——负值
一律不进分位数，而一个看起来合理的值会毁掉这个机制。折成 0 足以把 FAIL 翻成 PASS。

## 坑（两个都会伪装成「没数据」）

**日志时间戳是本地时间。** loguru 默认写本地时间，而窗口用 `datetime.now()` 算。这里
若按 UTC 解析，会静默丢掉最近若干小时——在 UTC+8 的机器上就是**你刚跑的那一次**——
报表打印「No bus hops in this window」，读起来像"功能没在记录"。`_line_time` 刻意返回
**naive 本地** datetime。

**轮转后的旧日志是 `.zip`。** 只有当天是 `.log`，30 天里其余全是压缩包。只 glob
`*.log` 会把「30 天报表」悄悄变成「今天报表」。`_iter_log_lines` 同时读两者，且单个
坏档只损失它自己那些行——一个碰到坏文件就整体崩掉的诊断工具，比只报告其余部分的更糟。
