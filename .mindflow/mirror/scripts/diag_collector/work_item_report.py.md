# work_item_report.py — 交接到底有没有回来

## 为什么存在

PR #230 的立场是：上更强的平台兜底之前，先要有测量。`make latency-report` 量的
是一跳**多快**，没有任何东西量过它**闭没闭**。于是「有多少交接最后没人回来」这
个数字不存在，「要不要做平台代交付」也就无从判断——这个脚本就是那个数字。

读 [[errand]] 和 [[patrol]] 写的 `[work-item]` 日志行。

## 为什么读日志不建表

沿用延迟报告那次的结论，不重新论证：loguru 已经按天轮转、留 30 天，数据本来就
在盘上；「日志会轮转掉，用 DB」那条教训针对的是 `docker logs`。

这里还有一条本地的理由：**板子本身就是表，缺的不是状态而是历史**——一个开了又
闭的项在表里只留下终态那一行，而算比率要的正是历史。

## 三个会让诊断悄悄说谎的坑

- **比率不能超过 100%**：窗口内闭环、但窗口外开的项没有 open 行可配对，把它算
  进分子就会让分子大过分母。这类闭环单独计数并在输出里说明。
- **stalled 按状态迁移记一次**：巡查每轮都会重新推导 stalled，按轮记会让一次断
  链读成几百次。这条约束落在**生产端**（patrol），消费端的测试是它的回归网。
- **默认不混 origin**：`tool` 是任务、`auto` 是差事，混在一起「闭环率」就同时表
  示两件事。`--all-origins` 才合并。

时间戳按**本地时**解析、轮转档是 `.zip` —— 与 [[latency_report]] 同款处理，两个
坑都以「没有数据」的形式失败，而那是诊断最坏的失败方式（读起来像「功能没在记
录」）。
